### 1. Архітектурний підхід

TripFlow — настільний застосунок WPF (C#, .NET) з локальною базою MS SQL Server LocalDB. Обрано **шарову архітектуру з шаблоном MVVM**:

```
View (XAML) → ViewModel → BLL (сервіси) → DAL (репозиторії, ADO.NET) → LocalDB
```

Головні правила:

* кожен шар звертається лише до наступного шару вниз;
* уся бізнес-логіка та валідація знаходиться в BLL, а не у вікнах;
* BLL оголошує інтерфейси репозиторіїв, а DAL їх реалізує, тому сервіси можна тестувати без бази даних;
* об'єкти створюються в одному місці через Dependency Injection (`App.xaml.cs`).



### 2. Структура рішення

```
TripFlow.sln
├── src/
│   ├── TripFlow.Models/   сутності та enum-и
│   ├── TripFlow.BLL/      сервіси, інтерфейси репозиторіїв, OperationResult
│   ├── TripFlow.DAL/      репозиторії, SqlConnectionFactory, DatabaseInitializer
│   └── TripFlow.UI/       Views, ViewModels, діалоги, appsettings.json
├── tests/
│   └── TripFlow.Tests/    модульні та інтеграційні тести
├── Documents/
└── UI/
```

Залежності: `UI → BLL`, `DAL → BLL`, `BLL → Models`, `DAL → Models`, `Tests → BLL, DAL`. UI посилається на DAL лише для підключення реалізацій у DI.

Основні пакети: `Microsoft.Data.SqlClient` (БД), `CommunityToolkit.Mvvm` (MVVM), `Microsoft.Extensions.DependencyInjection` (DI), `Serilog` (логи), `xUnit` + `Moq` (тести), PDF-бібліотека (QuestPDF або PDFsharp).

### 3. Основні компоненти та їх відповідальність

| Компонент | Що робить | Чого не робить |
|---|---|---|
| **Views** | Показують дані, прив'язки до ViewModel | Без логіки, без доступу до БД |
| **ViewModels** | Стан екрана, команди, виклик сервісів, показ помилок | Не рахує бюджет, не знає SQL |
| **TripService** | Створення, редагування, видалення поїздки, валідація дат і бюджету, статус за датами, фільтри | Не знає про WPF |
| **ItineraryService** | Генерація днів за датами, робота з активностями, сортування за часом | Не зберігає дані сам |
| **BudgetService** | Додавання й видалення витрат, розрахунок залишку та відсотка використання | — |
| **PackingService** | Речі чек-листа, відмітка «спаковано», відсоток зборів | — |
| **DataTransferService** | Експорт і імпорт поїздки у JSON | Не відкриває діалоги вибору файлу |
| **ReportService** | Формування PDF-звіту | — |
| **Репозиторії** | Параметризовані SQL-запити через ADO.NET, перетворення рядків у сутності | Без бізнес-правил і розрахунків |
| **DatabaseInitializer** | Створює базу та таблиці при першому запуску | — |

Моделі (`Trip`, `Activity`, `Expense`, `PackingItem`) — прості класи даних без логіки. Розрахунки залишку й відсотка виконують сервіси, а не `Trip`.

4. Модель даних
Ключові правила в базі:
усі обов'язкові поля NOT NULL;
Budget >= 0, Amount > 0, EndDate >= StartDate;
категорії витрат і речей обмежені списком із enum (CHECK);
гроші зберігаються як DECIMAL(18,2);
видалення поїздки видаляє її активності, витрати й речі (ON DELETE CASCADE);
індекси на TripId, для активностей на TripId, Date, Time (швидке сортування за часом).
Правила, які перевіряє сервіс (їх неможливо виразити в CHECK):
дата активності в межах дат поїздки;
дати поїздки не можна змінити так, щоб наявні активності вийшли за діапазон;
дата витрати не обмежена датами поїздки, бо оплата можлива до виїзду.
Дні подорожі й статус не зберігаються, вони обчислюються за датами: Planned (ще не почалась), InProgress (триває), Completed (завершилась). Фільтр «Заплановані» показує Planned та InProgress, «Завершені» показує Completed.

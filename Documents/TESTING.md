# Стратегія тестування TripFlow

## 1. Мета і підхід

Ми автоматично тестуємо **бізнес-логіку** (шар BLL) і **роботу з базою даних** (шар DAL), бо саме там живуть правила застосунку: валідація, розрахунок бюджету, статус поїздки, імпорт та експорт даних.

Інтерфейс (WPF, шар UI) ми перевіряємо **вручну** за сценаріями з `SCENARIOS.md`. Завдяки архітектурі MVVM ViewModel не містить бізнес-правил, а лише викликає сервіси. Тому логіку, яку потрібно перевіряти, покривають тести сервісів.

Інструменти:

| Інструмент | Призначення |
|---|---|
| xUnit 2.9 | Тестовий фреймворк (`[Fact]`, `[Theory]` + `[InlineData]`) |
| Moq 4.21 | Заглушки репозиторіїв у модульних тестах |
| SQL Server LocalDB | Справжня база для інтеграційних тестів |
| coverlet | Збір покриття коду (`--collect:"XPlat Code Coverage"`) |

## 2. Рівні тестування

### 2.1. Модульні тести (unit)

- Тестують **один сервіс** без бази даних.
- Репозиторій замінюємо заглушкою Moq. Так ми керуємо тим, що «повертає база», і перевіряємо, чи сервіс щось зберіг (`Verify(..., Times.Never)`).
- Тести швидкі (мілісекунди) і запускаються на будь-якому комп'ютері.

Приклад (`TripServiceTests`): якщо назва поїздки порожня, сервіс повертає помилку, а метод репозиторію `AddAsync` **жодного разу** не викликається.

### 2.2. Інтеграційні тести (integration)

- Перевіряють **справжні репозиторії ADO.NET і SQL-схему** на LocalDB.
- `LocalDbFixture` створює для кожного запуску окрему тимчасову базу `TripFlow_Tests_<guid>`, застосовує `Schema.sql` через `DatabaseInitializer`, а після тестів видаляє базу. Робоча база `TripFlow` не змінюється.
- Позначені `[Trait("Category", "Integration")]`, тому їх можна запускати окремо.
- Сервер можна змінити змінною середовища `TRIPFLOW_TEST_SQL_SERVER` (за замовчуванням `(localdb)\MSSQLLocalDB`).

## 4. Крайові випадки

Для кожного правила ми перевіряємо значення **на межі** та **одразу за межею**.

| Правило | Проходить | Не проходить |
|---|---|---|
| Бюджет поїздки ≥ 0 | `0` | `-0.01` |
| Дата завершення ≥ дати початку | поїздка на 1 день | завершення на день раніше |
| Назва поїздки ≤ 255 символів | 255 символів | 256 символів |
| Назва не порожня | `"Карпати"` | `""`, `"   "` |
| Статус поїздки 1–5 грудня | 30.11 → Заплановано; 1.12, 3.12, 5.12 → У процесі | 6.12 → Завершено |
| Активність у межах дат поїздки | перший і останній день | день до початку, день після завершення |
| Сума витрати > 0 | `620` | `0`, `-100` |
| Вартість активності | не вказана, `0` | від'ємна |
| Імпорт JSON | коректний файл; файл без списків | порожній файл, зламаний JSON, невідома версія формату |

Крайові випадки на рівні бази (інтеграційні тести):

- назва `O'Brien'); DROP TABLE dbo.Trips; --` зберігається як звичайний текст: параметризовані запити захищають від SQL-ін'єкції;
- видалення поїздки каскадно видаляє її активності, витрати й речі;
- витрату із сумою `0` відхиляє сама база (`CHECK Amount > 0`), навіть якщо обійти сервіс;
- повторний запуск `DatabaseInitializer` не ламає схему.

## 5. Рефакторинг

Під час написання тестів ми переробили два сервіси.

### 5.1. `PackingService`: помилки через `OperationResult` (PR #80, #81)

| Було | Стало |
|---|---|
| `AddAsync` при некоректних даних кидав `ArgumentException` | `AddAsync` повертає `OperationResult<int>` з текстом помилки |
| ViewModel ловив винятки через `try/catch` | ViewModel перевіряє `result.IsSuccess` і показує `ErrorMessage` |
| Відсоток пакування рахувався у ViewModel | `PackingService.CalculateProgress` рахує його в одному місці |

**Навіщо:** некоректне введення є очікуваною ситуацією, а не винятковою. Тепер усі сервіси повідомляють про помилки однаково, а результат легко перевірити в тесті.

### 5.2. `TripService`: валідація і статус у сервісі (PR #82)

| Було | Стало |
|---|---|
| Правила (порожня назва, порядок дат, від'ємний бюджет) перевіряла форма `TripFormViewModel` | Правила перевіряє `TripService.Validate`; форма перевіряє лише формат введення |
| Статус поїздки рахувався в UI рядками `"Completed"` / `"InProgress"` | `TripService.GetStatus(trip, today)` повертає `enum TripStatus` |
| Логіку можна було перевірити лише вручну через інтерфейс | 18 модульних тестів у `TripServiceTests` |

**Навіщо:** бізнес-правила живуть в одному шарі (BLL), не дублюються і тестуються без запуску WPF. Дата «сьогодні» передається параметром, тому тест статусу не залежить від дня запуску.

## 6. Як запускати

З кореня репозиторію:

```powershell
# усі тести
dotnet test

# лише модульні (без бази даних)
dotnet test --filter "Category!=Integration"

# лише інтеграційні (потрібен SQL Server LocalDB)
dotnet test --filter "Category=Integration"

# з покриттям коду
dotnet test --collect:"XPlat Code Coverage"
```

Якщо LocalDB не запускається:

```powershell
sqllocaldb stop MSSQLLocalDB
sqllocaldb start MSSQLLocalDB
```

## 7. Правила для команди

1. Нове бізнес-правило в сервісі додається **разом із тестом** у тому ж PR.
2. Назва тесту має формат `Метод_Умова_ОчікуванийРезультат`, наприклад `AddAsync_NegativeBudget_ReturnsFailureAndDoesNotSave`.
3. Кожен тест має структуру Arrange → Act → Assert.
4. Перед створенням PR усі тести мають проходити локально (`dotnet test`).

## 8. Що поки не покрито
